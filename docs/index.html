mon_brain — local Ollama note organizer / translator-summary / review tool

Languages / Langues / 语言：English · 中文 · Français · 📖 在线文档 / Docs / Documentation

← 中文版本 / Chinese version

A command-line tool running on your local Ollama: read source material → auto-split long text and merge summaries → apply the per-mode prompt → call the local model → export Markdown to sortie/. Data never leaves this machine; it does not depend on the teacher's workshop project, only reusing the same Ollama calling approach.

Directory layout

mon_brain\
├── mon_brain.py        # CLI main script (comments in English for reviewers)
├── app_web.py          # local web UI (standard-library server, same kernel reused)
├── corrections.txt     # static transcription correction table (misspelling -> correct word, editable)
├── prompts\            # per-mode prompts (change requirements here, not in code)
│   ├── organize.md
│   ├── translate_summary.md
│   └── recap.md
├── sources\            # staging folder; _upload\ holds temporary web uploads (auto-generated)

├── sortie\             # generated Markdown output (new file each run; originals are never overwritten)
└── .venv\              # isolated virtual environment (requests, pypdf installed)

GPU / compute configuration (measured on this laptop, 2026-11-23)

Ollama is configured for an RTX 5070 Ti Laptop GPU (12 GB VRAM) via user environment variables; re-apply with configure_ollama.ps1 after a fresh install.

VariableValueEffect
OLLAMA_FLASH_ATTENTION1Flash Attention: faster warmup and lighter KV cache
OLLAMA_KV_CACHE_TYPEq8_0halves KV-cache memory with negligible quality loss
OLLAMA_NUM_PARALLEL1serial long-document runs, avoids VRAM blow-up
OLLAMA_MAX_LOADED_MODELS1one 12B model at a time
OLLAMA_KEEP_ALIVE30mno 15–20 s reload before every run

Verified state: ollama ps shows 100% GPU; the server log reports offloaded 49/49 layers to GPU, flash_attn = enabled, K (q8_0) / V (q8_0).

Context window defaults to 8192 (override with MB_NUM_CTX). Warm measurements for one gemma3:12b answer: 8192 → 27.6 s / 8.7 GB; 12288 → 34.3 s / 8.9 GB. 8192 is the sweet spot; 24% slower otherwise.

Hybrid pipeline (--map-model): chunk summaries by a fast model, final note by the strong one. On a 28 694-char French transcript: pure gemma3:12b 344 s vs hybrid (qwen2.5:latest + gemma3:12b) 106 s (~3.2x). Two safeguards matter:

  • the map stage has a hard token cap (MAP_PREDICT=420), because small models ignore "be brief";
  • re-compression always uses the strong model, since a weak one echoes its input and stalls the loop.

Web UI presets: Fast (single qwen2.5:latest), Balanced (chunk qwen2.5 + final gemma3:12b), Quality (pure gemma3:12b). The output YAML header records map_model.

How it works: why a long source gets *faster*

A 28 694-char French lecture transcript takes 344 s with gemma3:12b alone and 106 s with the hybrid pipeline. The gain does not come from running agents in parallel: it comes from shrinking the work done at every step and paying for the expensive model only once.

source (>5000 chars)
   │  split_text: 3500 chars/chunk, 200-char overlap (no cut sentences, no lost context)
   ▼
[map] one call per chunk -> rough bullets, num_predict=420 (~800 chars cap)
      sequential on purpose: Ollama runs NUM_PARALLEL=1, parallel chunks would contend for VRAM
   ▼
merged summary
   │  only if still over budget -> reduce_to_budget: hierarchical re-compression
   │  with the strong model, max 3 rounds, stops when compression stalls
   ▼
[final] system + task prompt + language rule + your intent + merged summary -> the note

Budget: NUM_CTX=8192 minus the output reserve minus ~700 instruction tokens, estimated at CHAR_PER_TOKEN=2 → roughly 8 700 safe characters per single run.

Three reasons it is faster: (1) the 12B model writes only the final note, roughly 2.6x slower per token than the 7B one; (2) generation time scales with output length, and every chunk is capped at 420 tokens instead of free-running for thousands; (3) it avoids the expensive route where a 28k source blows the context and gemma3 has to re-compress round after round, each round a full generation.

How this differs from "multiple sub-agents": chunking is a fixed map-reduce pipeline — same prompt, stateless, no cross-talk, no decisions — it just turns one oversized request into several short ones. Sub-agents each carry their own goal, tools and planning. The speedup here comes from *less total work*, not from concurrency.

One-click start (Windows)

Double-click start.bat instead of typing the command. It checks five things in order and stops with a readable message at the first failure:

  1. .venv\Scripts\python.exe exists (otherwise: create the venv and install requests / pypdf).
  2. GPU: prints the card and VRAM via nvidia-smi; if it is missing it warns that runs will fall back to CPU (5–20× slower).
  3. Ollama: reuses it when already listening, otherwise starts ollama serve with the GPU flags FLASH_ATTENTION=1, KV_CACHE_TYPE=q8_0, NUM_PARALLEL=1, MAX_LOADED_MODELS=1, KEEP_ALIVE=30m.
  4. Preset models: qwen2.5:latest / gemma3:12b / qwen3:14b. A missing one produces a warning with the exact ollama pull command — it never starts a 40 GB download on its own.
  5. Port 5000: reuses the server only when GET /api/state answers like mon_brain; if some other program holds the port it aborts instead of hijacking it.

GPU needs no configuration — it is already in use. Measured here (RTX 5070 Ti Laptop, 12 227 MiB): gemma3:12b reports size_vram 7.30 GB / size 7.30 GB, i.e. 100 % resident on the GPU, load plus a short answer ≈ 13 s.

Only one model is resident at a time. 12 GB of VRAM fits exactly one preset model (qwen3:14b is the heaviest at 8.6 GB of weights), so switching presets reloads it: expect tens of seconds. That is MAX_LOADED_MODELS=1 working as intended, not a hang.

Examples

Open PowerShell in this folder:

# Use the venv Python directly (no activation needed)
$py = ".\.venv\Scripts\python.exe"

# 1) Single file: summary + organizing (default mode, Chinese body)
& $py mon_brain.py "C:\path\to\notes\lecture.txt" --lang bilingual

# 2) Process every file in a folder into its own note
& $py mon_brain.py "C:\path\to\notes" --mode organize

# 3) Merge all files in the folder into one note (shared context across files)
& $py mon_brain.py "C:\path\to\notes" --mode organize --merge

# 4) Recap mode (keeps thinking chain, evaluates the question + self-check), then enter a follow-up loop
& $py mon_brain.py sources\test_recap.txt --mode recap --interactive

# 5) Continue the previous recap session (multi-turn follow-up)
& $py mon_brain.py sources\test_recap.txt --mode recap --continue

# 6) Override the model; --fresh ignores the previous draft and starts over
& $py mon_brain.py sources\xxx.docx --mode recap --model deepseek-r1:8b --fresh

# 7) List the available prompt files
& $py mon_brain.py --list-prompts

Web UI checks (run after every front-end edit)

The UI ships as one inline <script>; a single missing bracket stops the whole script, so language buttons, compute presets and upload all look "dead". Run this first:

.\.venv\Scripts\python.exe tools\check_page.py

It validates JS syntax (node --check), i18n key coverage for en/zh/fr, and that every getElementById target exists in the HTML. Exit code 0 means clean.

Static correction table (corrections.txt)

Common speech-to-text misspellings (e.g. Olama → Ollama, Lama → Llama, LocalRoss → localhost) are listed in corrections.txt. The script loads it at startup and injects it into the prompt so the model restores the correct words.

  • Format: wrong => correct # note; lines starting with # are comments.
  • The [uncertain] section lists items to confirm; they are marked uncertain in the output and never stated as fact.
  • Add your own frequent misspellings at any time.

Incremental update

When the same source (same mode, same file name) is processed again, the script automatically finds the latest previous draft in sortie\ and injects it as the "previous draft", so it revises and supplements it instead of starting over. Pass --fresh to disable this. Old drafts are never overwritten.

Merge mode and session memory

  • Merge mode --merge: each file is summarized first; earlier files' conclusions are carried forward as background context for later files, then everything is fused into one note. The output header source lists all input files.
  • Recap sessions: the first recap exchange is stored in sessions\<source>.json; --interactive lets you keep asking after the first draft, and --continue resumes the last history next time. Follow-up turns are appended to the same Markdown note.

Output rules

  • File name: date_mode_source.md; an existing name gets an incremented number — originals are never overwritten.
  • YAML header: source file, mode, model, language, date; recap notes also reference the session file.
  • Long material: over ~5000 characters it is auto-split into chunks, each summarized, then merged into one note (no hard truncation).
  • If the merged source is still too long, a warning suggests processing it in separate runs.
  • Recap mode: two calls — material review first, then question evaluation + self-check; the thinking chain is kept in its own section; stray outer Markdown fences are stripped automatically.

Current limitations (later batches)

  1. Repeated recap sections (fixed): the second call often re-emits all three sections. strip_repeated_sections now truncates at the first repeated heading (4 836 -> 2 501 chars in a real run), and prompts/recap.md states "write each section once".
  2. Paragraph parallel text is unreliable: local 12B models do not consistently follow "append a foreign parallel to key paragraphs"; most of the time only the trilingual glossary is produced.
  3. Generation length cap: about 2048–2560 tokens per call; very long answers may still end incompletely.
  4. Scanned PDFs cannot be read: image PDFs need OCR (llava / easyocr), not yet integrated.
  5. Model ceiling: local 7B–12B models are weaker than cloud models in French idiomaticness, long-text logic, and English term rendering; review the output yourself and do not treat uncertain items as fact.
  6. To do: source-code project parsing, scanned-PDF OCR, segmented continuation of long answers; the web result area currently shows Markdown as plain text, rich rendering is left for later.

Troubleshooting

  • Cannot reach Ollama / Connection refused: make sure Ollama is running (taskbar icon, or run ollama serve in another terminal).
  • model not found: the model name does not match ollama list; use --model with the exact name from the list.
  • PDF yields no text: most likely a scanned image PDF; OCR is not supported in this version.
  • Garbled Chinese/French text: the script forces UTF-8; if the console still garbles, make sure you are using the .venv Python.

算力配置（本机最优档，2026-11-23 实测）

显卡 RTX 5070 Ti Laptop 12 GB、内存 31 GB。Ollama 已按下表配好（用户级环境变量，重启 Ollama 生效），配置脚本见 configure_ollama.ps1：

上下文窗口：默认 8192（MB_NUM_CTX 可覆盖）。实测 gemma3:12b 热态下单次输出：8192 → 27.6 秒 / 8.7 GB 显存；12288 → 34.3 秒 / 8.9 GB 显存（仍 100% GPU）。结论：8192 是甜点，12288 慢 24%，只有在单份素材必须一次塞进去时才用。

混合流水线（--map-model）：分片摘要用快模型、终稿用精模型。28 694 字符法语转写实测：纯 gemma3:12b 344 秒；混合（qwen2.5:latest 分片 + gemma3:12b 终稿）106 秒，约 3.2 倍。

  • 分片阶段有 token 硬上限 MAP_PREDICT=420（约 800 字符/片），光靠提示词约束小模型不可靠（实测它会写到 2 000+ 字符/片，把速度优势吃光）。
  • 二级压缩固定用精模型：弱模型会把输入原样吐回，导致压缩停滞、整篇被误判为"超预算"而拒稿。
  • Web 界面新增三档算力预设：极速（qwen2.5:latest 单模型）/ 均衡（分片 qwen2.5 + 终稿 gemma3:12b）/ 高质（纯 gemma3:12b，数字与结构最准但最慢）。
  • 出稿 YAML 头部会记录 map_model，回看可知这份是怎么跑的。

原理与架构：长素材为什么反而更快

处理一条 28 694 字符的法语课转写，纯用 gemma3:12b 跑要 344 秒，混合流水线只要 106 秒。原因不是"多开几个 agent 并行"，而是把每一步的工作量压小、把贵的那一步只做一次。

流水线（mon_brain.py 里的 process_one）：

素材（>5000 字符）
   │  split_text: 3500 字符/片，相邻重叠 200 字符（防止切断句子与上下文）
   ▼
[map] 每片单独调用 → 粗提炼，num_predict=420（约 800 字符上限）
      └ 顺序执行，不是并行：Ollama 设为 NUM_PARALLEL=1，片上并行会抢显存
   ▼
合并稿（各片要点拼接）
   │  若仍超过单次预算 → reduce_to_budget: 用精模型层级再压缩，最多 3 轮，压缩停滞即停
   ▼
[reduce] 合并稿 ≤ 预算（约 8700 字符）
   ▼
[final] 系统指令 + 任务提示词 + 语言要求 + 你的意图 + 合并稿 → 终稿

预算怎么来：NUM_CTX=8192 减去输出预留，再减去指令预留（约 700 token），按 CHAR_PER_TOKEN=2 估算，得约 8700 字符的安全上限。超过就先分片；分片后仍超，才动第二级压缩。

为什么变快（三条，缺一不可）：

  1. 贵模型只写一次。gemma3:12b 每 token 约为 qwen2.5:latest 的 2.6 倍耗时，所以让它只做"终稿"这一件事，粗活交给小模型。
  2. 输出被 token 上限钉死。生成时间是输出长度的线性函数：每片限 420 token，9 片合计约 3 800 token，而不是让模型自由发挥写出两三万字。
  3. 避免了"大模型反复压缩"的路。单次塞 28k 会直接超上下文，只能靠 gemma3 一轮轮压缩，而每次压缩本身又是全量生成——纯 gemma3 那 344 秒大部分花在这里。混合方案的分片后合并稿只有 7 587 字符，一次就进终稿，压缩轮数为 0。

它和"多个子 agent"的区别：分片是固定流水线（map-reduce），同一套提示词、无状态、互相不通话、不做决策，只是把一次超长的请求切成若干次短请求；子 agent 是各自带目标、带工具、会自己规划下一步的独立执行者。前者能省时间是因为总量变小，不是因为有并行度。

相关常量（mon_brain.py 顶部）：SPLIT_THRESHOLD=5000、CHUNK_SIZE=3500、CHUNK_OVERLAP=200、MAP_PREDICT=420、NUM_CTX=8192、MAX_REDUCE_ROUNDS=3、CHAR_PER_TOKEN=2。

  • 完全离线可用：Tailwind 已本地化到 static\tailwind.js（页面从 /static/tailwind.js 加载，不再请求 CDN）；新机器上若缺文件，跑 tools\fetch_vendor.ps1 一次即可。断网、无外网教室都能正常显示。
  • /docs 说明页：顶部「说明 / Docs」会在新标签打开 http://127.0.0.1:5000/docs，直接把本 README 渲染成网页（可切中文 / English / Français），原理、架构、参数表、实测数据都在里面，适合用完后回来复习。右上角可返回工作台。
  • 处理过程可见：点开始后结果区上方会实时滚动进度日志（读取素材 → 分片 i/n → 调用模型 → 保存），不再是一块"假死"的静止画面。
  • 调试视图：勾选「显示调试信息」，出稿后会附带实际使用的系统指令、任务提示词、语言要求、分片数、上下文字符预算、素材字符数等，便于对照排查。
  • 多会话切换：「复盘会话」区列出 sessions\ 里所有会话，点 open 直接载入历史对话气泡，可接着追问。
  • 提示词模板可编辑：「提示词模板」区可下拉选择 prompts\*.md，直接编辑并保存回原文件，不用再开编辑器。
  • 输出两档：
  • 中文总结 + 对照（默认）：中文正文 + 所选对照语言 + 三语术语表；
  • 跟随素材语言整篇：整篇用素材语言输出（法语素材出法语、英语素材出英语），不切中文。
  • 支持：多选文件上传、模式/对照语言/模型选择、多文件合并勾选、全新开始开关、复盘对话式追问、历史稿件查看与下载。
  • 复盘模式有一个可选「意图 / 你的提问」输入框（对应命令行 --intent）；留空则只复盘素材本身。
  • 连不上本地 Ollama 时，结果区会用红色醒目提示去启动 Ollama。
  • 网页上传的文件临时存在 sources\_upload\，超过 24 小时的临时目录会在下次上传时自动清理；生成的正式稿件仍落在 sortie\。

Windows 一键启动

不想敲命令就双击项目根目录的 start.bat。它按顺序查五件事，第一件不通过就停在那里并给出人话提示：

  1. .venv\Scripts\python.exe 在不在（不在就提示先建环境、装 requests / pypdf）。
  2. GPU：用 nvidia-smi 打印显卡型号和显存；没有 nvidia-smi 就警告"会退回 CPU，慢 5–20 倍"。
  3. Ollama：已在监听就直接复用；否则后台起 ollama serve，并显式注入 GPU 参数 FLASH_ATTENTION=1、KV_CACHE_TYPE=q8_0、NUM_PARALLEL=1、MAX_LOADED_MODELS=1、KEEP_ALIVE=30m（这些参数必须先于服务启动生效，继承来的旧环境变量不算数）。
  4. 三档所需模型：qwen2.5:latest / gemma3:12b / qwen3:14b；缺哪个就提示对应的 ollama pull 命令，不会自作主张替你下 40 GB。
  5. 5000 端口：只有 GET /api/state 返回的确实是 mon_brain 才复用；端口被别的程序占着就报错退出，不会把别人当成自己的服务。

GPU 不用配置，它已经在用。 本机实测（RTX 5070 Ti Laptop，12 227 MiB）：gemma3:12b 的 size_vram 7.30 GB / size 7.30 GB，即 100% 驻留显存，加载加一次短回答约 13 秒。

同一时刻只驻留一个模型。 12 GB 显存刚好放得下一个档位的模型（最重的 qwen3:14b 权重 8.6 GB），所以来回切档位会重新加载模型，等十几秒属正常——那是 MAX_LOADED_MODELS=1 在起作用，不是卡死。

命令示例

在本目录打开 PowerShell：

# 直接用 venv 的 Python（无需激活）
$py = ".\.venv\Scripts\python.exe"

# 1) 单个文件：总结 + 整理（默认模式，中文正文）
& $py mon_brain.py "C:\path\to\notes\lecture.txt" --lang bilingual

# 2) 整个文件夹逐个生成 md
& $py mon_brain.py "C:\path\to\notes" --mode organize

# 3) 多文件合并成一篇（文件间共享上下文）
& $py mon_brain.py "C:\path\to\notes" --mode organize --merge

# 4) 复盘模式（保留思考链，评估问法 + 自检），并进入追问循环
& $py mon_brain.py sources\test_recap.txt --mode recap --interactive

# 5) 续接上次复盘会话（多轮追问）
& $py mon_brain.py sources\test_recap.txt --mode recap --continue

# 6) 手动指定模型；--fresh 表示不沿用上次草稿，从头生成
& $py mon_brain.py sources\xxx.docx --mode recap --model deepseek-r1:8b --fresh

# 7) 查看有哪些提示词文件
& $py mon_brain.py --list-prompts

数字保真自检

终稿生成后会做一次机械校对：把素材里的"数字 + 单位"（如 40%、10 points、3部、6篇）和"三位数以上/反复出现的独立数字"（如课程号 102）抽出来，逐个确认是否出现在终稿里。

  • 有缺失：CLI 打印 ⚠ 数字保真自检…缺 X 项，Web 结果区上方弹琥珀色黄条，列出缺失项；md 头部记 fidelity_missing: N。
  • 全在：CLI 打印 ✓ 数字保真自检通过，Web 不打扰。
  • 这是启发式提醒，不是证明：它能抓"数字被丢掉/被改写"，但判断不了"数字挂错了条件"。所以黄条出现时请人工看一眼，别直接打印。

改前端后必跑：页面自检

app_web.py 的界面是一整段内联 JS，一个括号写错就会让整段脚本不执行——表现是"语言按钮没反应、档位按钮没反应、上传也没反应"，很像前端事件没绑，实际是语法错误。改完必须先跑：

.\.venv\Scripts\python.exe tools\check_page.py

它做三件确定性检查：

检查抓什么
JS 语法（调用 node --check）缺括号、逗号、引号等，直接给出行号
三语词典覆盖data-i18n 用到的键在 en/zh/fr 里是否齐全（缺键会显示原始键名，看着像切语言失效）
getElementById 目标脚本里引用的 id 是否真的存在于 HTML（拼错就会绑到 null）

退出码 0 才算通过。这个脚本做过反向验证：故意删一个 );，它会失败并指出第 87 行。

静态误写对照表（corrections.txt）

语音转写里的常见错拼（如 Olama → Ollama、Lama → Llama、LocalRoss → localhost）写在 corrections.txt，脚本按素材内容命中后才注入提示词（剥离标点、忽略大小写、按词边界匹配），素材里没出现的条目不会塞进提示词，避免污染输出。

  • 格式：错拼 => 正确词 # 备注；# 开头为注释。
  • [uncertain] 区段为待确认项，输出时会标注存疑，不会当成定论。
  • 你可以随时往里增补自己遇到的高频错拼。

增量更新

再次处理同一素材（同模式、同文件名）时，脚本会自动在 sortie\ 找最新一版旧稿，作为「上一版草稿」注入，在其基础上补充、修订，而不是从头再来。加 --fresh 可关闭此行为。旧稿永远不会被覆盖。

多文件合并与会话记忆

  • 合并模式 --merge：逐文件先出要点摘要，前序文件的结论作为后续文件的背景上下文，最后融合成一篇总稿；输出头部 source 记录全部来源文件。
  • 复盘会话：复盘的首轮问答会存入 sessions\<素材名>.json；--interactive 可在首稿后继续追问，--continue 下次接着上次的历史聊。追问记录会追加到同一篇 md。

输出规则

  • 文件名：日期_模式_素材名.md；同名已存在自动加序号，不覆盖原稿。
  • md 头部 YAML 元信息：来源文件、模式、模型、语言、日期；复盘稿附会话文件名。
  • 长素材：超过约 5000 字符（或超过单次上下文预算）自动分片，逐片出要点摘要再合并成一篇；合并稿若仍超预算，会自动再压缩（最多 3 轮），仍放不下才提示你拆分处理，不硬截断。
  • 合并后素材仍过长时，会给出警告，提示拆成多次处理。
  • 复盘模式：拆两段调用——先出素材复盘，再出问法评估 + 自检；思考链单独成节；外层多余 Markdown 围栏会被自动剥掉。

当前限制（后续批次再做）

  1. 复盘重复段落（已修）：模型常在第二段把三大部分整篇重抄一遍。已加 strip_repeated_sections：按标题文本去重，遇到重复标题就截断（实测 4 836 → 2 501 字符）；同时 prompts/recap.md 明确「每部分只写一次」。
  2. 段落对照执行不到位：本地 12B 模型对「关键段落附外文对照」的遵循不稳定，多数时候只在术语表给出三语对照；正文段落对照可能缺失。
  3. 生成长度上限：单次输出上限约 2048–2560 token，极长回答结尾仍可能不完整。
  4. 扫描版 PDF 读不了：图片型 PDF 需要 OCR（llava / easyocr），尚未接入。
  5. 模型能力上限：本地 7B–12B 模型在法语地道度、长文逻辑、术语英译上不如云端大模型；输出需本人终审，存疑项不要当定论。
  6. 待做：源码项目解析、扫描 PDF OCR、分段续写长回答；网页结果区目前以纯文本展示 Markdown，富文本渲染留待后续。

常见报错

  • 连不上 Ollama / Connection refused：确认 Ollama 已启动（任务栏图标，或另开终端 ollama serve）。
  • model not found：模型名和 ollama list 里不一致；用 --model 改成列表里的精确名字。
  • PDF 读不出文字：大概率是扫描图片 PDF，当前版本不支持 OCR。
  • 中文/法语乱码：脚本已强制 UTF-8；如控制台仍乱码，确认用的是 .venv 里的 Python。

Outil en ligne de commande tournant sur votre Ollama local : lire la source → découper automatiquement les textes longs et fusionner les résumés → appliquer le prompt du mode → appeler le modèle local → exporter le Markdown dans sortie/. Configuration GPU / calcul (mesurée sur ce portable, 2026-11-23)

Ollama est réglé pour une RTX 5070 Ti Laptop (12 Go de VRAM) via des variables d'environnement utilisateur ; relancez configure_ollama.ps1 après une réinstallation.

VariableValeurEffet
OLLAMA_FLASH_ATTENTION1Flash Attention : plus rapide, KV cache plus léger
OLLAMA_KV_CACHE_TYPEq8_0mémoire du KV cache divisée par deux, perte de qualité négligeable
OLLAMA_NUM_PARALLEL1exécution sérielle des longs documents
OLLAMA_MAX_LOADED_MODELS1un seul modèle 12B en mémoire
OLLAMA_KEEP_ALIVE30mévite 15–20 s de rechargement à chaque exécution

Vérifié : ollama ps affiche 100% GPU ; le journal indique offloaded 49/49 layers to GPU, flash_attn = enabled, K (q8_0) / V (q8_0).

Fenêtre de contexte : 8192 par défaut (surchargeable via MB_NUM_CTX). Mesures à chaud pour gemma3:12b : 8192 → 27,6 s / 8,7 Go ; 12288 → 34,3 s / 8,9 Go. 8192 est l'optimum.

Pipeline hybride (--map-model) : résumés de fragments par un modèle rapide, note finale par le modèle fort. Sur une transcription française de 28 694 caractères : gemma3:12b seul 344 s vs hybride (qwen2.5:latest + gemma3:12b) 106 s (~3,2x). Deux garde-fous : plafond de tokens à l'étape map (MAP_PREDICT=420) et recompression toujours confiée au modèle fort.

Profils de l'interface web : Rapide, Équilibré, Qualité. L'en-tête YAML des notes enregistre map_model.

Principe : pourquoi une source longue devient *plus rapide*

Une transcription française de 28 694 caractères prend 344 s avec gemma3:12b seul, 106 s avec la chaîne hybride. Le gain ne vient pas d'agents exécutés en parallèle, mais du fait qu'on réduit le travail de chaque étape et qu'on ne paie le gros modèle qu'une fois.

source (>5000 caractères)
   │  split_text : 3500 caractères/fragment, chevauchement de 200 (pas de phrase coupée)
   ▼
[map] un appel par fragment -> puces brutes, num_predict=420 (~800 caractères max)
      séquentiel volontaire : NUM_PARALLEL=1, des fragments en parallèle se disputeraient la VRAM
   ▼
résumé fusionné
   │  seulement si le budget est encore dépassé -> reduce_to_budget avec le modèle fort,
   │  3 tours maximum, arrêt dès que la compression stagne
   ▼
[final] consignes + prompt de tâche + règle de langue + votre intention + résumé -> la note

Budget : NUM_CTX=8192 moins la réserve de sortie et ~700 jetons d'instructions, estimé à CHAR_PER_TOKEN=2 → environ 8 700 caractères sûrs par exécution.

Trois raisons : (1) le 12B ne rédige que la note finale, environ 2,6 fois plus lent par jeton que le 7B ; (2) le temps de génération suit la longueur produite, et chaque fragment est plafonné à 420 jetons ; (3) on évite la voie coûteuse où une source de 28k dépasse le contexte et où gemma3 doit recompresser tour après tour.

Différence avec « plusieurs sous-agents » : le découpage est un pipeline map-reduce figé — même prompt, sans état, sans dialogue, sans décision — il transforme juste une requête trop longue en plusieurs courtes. Les sous-agents portent chacun un objectif, des outils et une planification. Ici le gain vient de *moins de travail total*, pas de la concurrence.

Politique de langue de sortie

Le corps du texte est toujours rédigé en chinois. --lang ne contrôle que la langue de parallèle pour les termes/paragraphes clés ; il ne produit jamais de résumé entier en langue étrangère. Le glossaire final est toujours trilingue : 中文 / English / Français.

enCorps chinois + parallèle anglais pour les termes/paragraphes clés
frCorps chinois + parallèle français pour les termes/paragraphes clés
bilingualCorps chinois + parallèle anglais et français
fr-zhalias historique de bilingual, conservé pour compatibilité

Démarrage en un clic (Windows)

Double-cliquez sur start.bat plutôt que de taper la commande. Il vérifie cinq points dans l'ordre et s'arrête au premier échec avec un message clair :

  1. .venv\Scripts\python.exe existe (sinon : créer le venv et installer requests / pypdf).
  2. GPU : affiche la carte et la VRAM via nvidia-smi ; en son absence, avertit que tout retombera sur le CPU (5 à 20 fois plus lent).
  3. Ollama : réutilisé s'il écoute déjà, sinon démarrage de ollama serve avec les paramètres GPU FLASH_ATTENTION=1, KV_CACHE_TYPE=q8_0, NUM_PARALLEL=1, MAX_LOADED_MODELS=1, KEEP_ALIVE=30m.
  4. Modèles des profils : qwen2.5:latest / gemma3:12b / qwen3:14b. Un modèle manquant déclenche seulement un avertissement avec la commande ollama pull — il ne lance jamais un téléchargement de 40 Go.
  5. Port 5000 : réutilisé uniquement si GET /api/state répond bien comme mon_brain ; sinon le script s'arrête au lieu de prendre le port d'un autre programme.

Le GPU n'a rien à configurer : il est déjà utilisé. Mesuré ici (RTX 5070 Ti Laptop, 12 227 Mio) : gemma3:12b affiche size_vram 7.30 GB / size 7.30 GB, soit 100 % résident sur le GPU, chargement plus réponse courte ≈ 13 s.

Un seul modèle résident à la fois. 12 Go de VRAM contiennent exactement un modèle d'un profil (qwen3:14b est le plus lourd, 8,6 Go), donc changer de profil recharge le modèle : comptez quelques dizaines de secondes. C'est MAX_LOADED_MODELS=1 qui agit, pas un blocage.

Exemples

Ouvrez PowerShell dans ce dossier :

# Utiliser directement le Python du venv (sans activation)
$py = ".\.venv\Scripts\python.exe"

# 1) Fichier seul : résumé + organisation (mode par défaut, corps chinois)
& $py mon_brain.py "C:\path\to\notes\lecture.txt" --lang bilingual

# 2) Traiter chaque fichier d'un dossier en note séparée
& $py mon_brain.py "C:\path\to\notes" --mode organize

# 3) Fusionner tous les fichiers du dossier en une seule note (contexte partagé)
& $py mon_brain.py "C:\path\to\notes" --mode organize --merge

# 4) Mode révision (chaîne conservée, évaluation de la question + auto-contrôle), puis boucle de suivi
& $py mon_brain.py sources\test_recap.txt --mode recap --interactive

# 5) Reprendre la session de révision précédente (suivi multi-tours)
& $py mon_brain.py sources\test_recap.txt --mode recap --continue

# 6) Surcharger le modèle ; --fresh ignore le brouillon précédent et repart de zéro
& $py mon_brain.py sources\xxx.docx --mode recap --model deepseek-r1:8b --fresh

# 7) Lister les fichiers de prompt disponibles
& $py mon_brain.py --list-prompts

Contrôles de l'interface (après chaque modification du front)

L'interface tient dans un seul <script> inline : une seule parenthèse manquante empêche tout le script de s'exécuter (boutons de langue, profils de calcul et upload semblent alors « morts »). À lancer avant tout test :

.\.venv\Scripts\python.exe tools\check_page.py

Il vérifie la syntaxe JS (node --check), la couverture des clés i18n en/zh/fr, et l'existence de chaque cible getElementById dans le HTML. Code de sortie 0 = tout est bon.

Table statique de corrections (corrections.txt)

Les fautes courantes de reconnaissance vocale (ex. Olama → Ollama, Lama → Llama, LocalRoss → localhost) sont listées dans corrections.txt. Le script la charge au démarrage et l'injecte dans le prompt pour que le modèle restaure les bons mots.

  • Format : faute => correct # note ; les lignes commençant par # sont des commentaires.
  • La section [uncertain] contient les éléments à confirmer ; ils sont marqués incertains dans la sortie et jamais présentés comme des faits.
  • Ajoutez vos propres fautes fréquentes à tout moment.

Mise à jour incrémentale

Lors du retraitement d'une même source (même mode, même nom de fichier), le script retrouve automatiquement le dernier brouillon dans sortie\ et l'injecte comme « brouillon précédent » : il le révise et le complète au lieu de repartir de zéro. --fresh désactive ce comportement. Les anciens brouillons ne sont jamais écrasés.

Fusion et mémoire de session

  • Mode fusion --merge : chaque fichier est d'abord résumé ; les conclusions des fichiers précédents servent de contexte aux suivants, puis tout est fusionné en une note unique. L'en-tête source liste tous les fichiers d'entrée.
  • Sessions de révision : le premier échange est stocké dans sessions\<source>.json ; --interactive permet de continuer à poser des questions après le premier brouillon, et --continue reprend l'historique suivant. Les tours de suivi sont ajoutés à la même note Markdown.

Règles de sortie

  • Nom de fichier : date_mode_source.md ; un nom existant reçoit un numéro incrémenté — les originaux ne sont jamais écrasés.
  • En-tête YAML : source, mode, modèle, langue, date ; les notes de révision référencent aussi le fichier de session.
  • Texte long : au-delà d'environ 5000 caractères, découpage en fragments, résumé de chaque fragment puis fusion en une note (pas de troncature brute).
  • Si la source fusionnée reste trop longue, un avertissement suggère de la traiter en plusieurs passages.
  • Mode révision : deux appels — révision de la source d'abord, puis évaluation de la question + auto-contrôle ; la chaîne de réflexion est conservée dans sa propre section ; les balises de bloc Markdown superflues sont retirées automatiquement.

Limites actuelles (lots ultérieurs)

  1. Sections de révision répétées (corrigé) : le second appel réémet souvent les trois sections. strip_repeated_sections coupe au premier titre répété (4 836 → 2 501 caractères sur un cas réel), et prompts/recap.md impose « chaque section une seule fois ».
  2. Parallèle de paragraphe peu fiable : les modèles locaux 12B ne suivent pas constamment « ajouter un parallèle étranger aux paragraphes clés » ; le glossaire trilingue est souvent seul produit.
  3. Plafond de longueur : environ 2048–2560 jetons par appel ; les très longues réponses peuvent rester incomplètes en fin.
  4. PDF scannés illisibles : les PDF image nécessitent une OCR (llava / easyocr), pas encore intégrée.
  5. Plafond du modèle : les modèles locaux 7B–12B sont moins bons que les modèles cloud sur l'idiomatique française, la logique longue et le rendu des termes anglais ; relisez la sortie et ne traitez pas les éléments incertains comme des faits.
  6. À faire : analyse de projet de code source, OCR des PDF scannés, continuation segmentée des longues réponses ; la zone de résultat web affiche actuellement le Markdown en texte brut, le rendu riche est à venir.

Dépannage

  • Impossible de joindre Ollama / Connection refused : vérifiez qu'Ollama tourne (icône dans la barre des tâches, ou lancez ollama serve dans un autre terminal).
  • model not found : le nom du modèle ne correspond pas à ollama list ; utilisez --model avec le nom exact de la liste.
  • PDF sans texte : très probablement un PDF image scanné ; l'OCR n'est pas pris en charge dans cette version.
  • Caractères chinois/français illisibles : le script force l'UTF-8 ; si la console reste garbled, vérifiez que vous utilisez le Python du .venv.
